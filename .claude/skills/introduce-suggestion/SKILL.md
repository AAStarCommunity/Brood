# introduce-suggestion — 介绍 + 进度 review + 下一步建议

你是 Brood / Mycelium 生态的协调员。当用户让你做项目自我介绍时，**永远不要只做单纯介绍**，必须给出三段式响应：

```
1. 核心能力介绍（30 秒电梯演讲）
2. 整体进度 review（Phase 1/2/3 + In Progress 重点）
3. 下一步 Focus 建议（1-3 项，含 repo、当前%、预期%、时机理由）
```

---

## 触发场景（自动激活）

用户说出以下任何一类话，立即用此 skill：

- 「介绍一下你自己 / 这个项目 / 这个 repo」
- 「你是谁 / 你是什么 / 你能做什么」
- 「Brood 是什么 / Mycelium 是什么」
- 「给我看看现状 / 我想了解项目情况」
- 「我刚加入 / 我是新来的」
- 「这个 report 它的核心能力」
- 「introduce / about / tell me about this」

---

## 执行流程

### 第 1 步 · 核心能力介绍（30 秒）

用 1-2 句话定位 Brood，然后列六大能力表格：

```
Brood 是 Mycelium Protocol 的「神经系统」—— 协议神经层 +
任务管理 + L0/L1/L2 生态 AI 上下文发布 + skill 自动化。

| # | 能力 | 关键文件 / 命令 |
|---|------|---------------|
| 1 | 项目管理 + 静态发版 | backlog + pnpm run build → CF Pages |
| 2 | 生态 AI 上下文      | protocol/ + orgs/ → 64 repo @-include |
| 3 | 进度扫描同步        | /sync-progress |
| 4 | License 合规        | /license-update |
| 5 | PGL 公约 L0          | protocol/PGL/ |
| 6 | 跨 repo 协作感知     | ECOSYSTEM_MAP + INTERFACES |
```

### 第 2 步 · 整体进度 review

读取 `backlog/docs/doc-7 - 📊-Progress-Report.md`，提取：
- 三个 Phase 的最新加权进度
- 重点 In Progress 任务（进度 ≥ 50% 或近期活跃的）
- 最近一次 sync-progress 扫描日期

输出格式：

```
## 整体进度（数据来源：doc-7，最近扫描 YYYY-MM-DD）

| Phase | 加权进度 | 任务数 | 重点变化 |
|-------|---------|-------|---------|
| Phase 1: Genesis Launch | **N%** | n 个 | 关键变化一句话 |
| Phase 2: Community Expansion | **N%** | n 个 | 关键变化一句话 |
| Phase 3: Ecosystem Maturity | **N%** | n 个 | 关键变化一句话 |

最活跃的 3-5 个任务：
- TASK-XX (进度%): 一句话状态
- TASK-YY (进度%): 一句话状态
```

### 第 3 步 · 下一步 Focus 建议（关键！）

这是 skill 的核心价值。从 In Progress 任务中筛选**「1-2 周内能从当前进度推到 90%+」**的候选，给出 1-3 个建议。

**筛选标准**：
1. 当前进度 ≥ 60%（接近完成线）
2. 最近 30 天有活跃 commit（团队还在做）
3. 剩余工作量可量化（不是开放性研究）
4. 完成后能解锁下游任务或对外发布

输出格式：

```
## 🎯 下一步 Focus 建议（基于「投入产出最优」原则）

### 建议 1：TASK-XX「<任务名>」
- **仓库**：org/repo
- **当前进度**：65% → **建议 2 周内推到 90%+**
- **关键缺口**：列出剩余 2-3 项 AC
- **为什么现在做**：解锁 X 任务 / 即将路演 / 上下游依赖等
- **建议下一周动作**：具体 1-2 件事

### 建议 2：...

### 建议 3：...
```

**避免建议**：
- 进度 < 50% 的（基础不够，不是 1-2 周冲刺范围）
- 已 100% Done 的
- 完全没有 commit 数据的（团队没动）
- 阻塞依赖外部（如等审计、等监管批复）

### 第 4 步 · 收尾问题

最后一段问用户：
> 「想了解某个建议的细节吗？或者想看其他维度（比如 Research / 长期任务）？」

## 执行注意事项

1. **数据来源优先级**：
   - `protocol/GOALS.md`（**OKR 视角**，半年期目标 + 节奏感 + 比赛时间表 + orchestrator 提醒规则）
   - `backlog/docs/doc-7 - 📊-Progress-Report.md`（**task 视角**，含 Phase 加权）
   - `docs/REPO_STATUS.md`（**repo 视角**，全 65 仓库健康度 + 关注列表）
   - `backlog/tasks/*.md`（单任务详情 + 预估进度）
   - `docs/ECOSYSTEM_MAP.md`（仓库地图）
   - `docs/DEPENDENCY_GRAPH.md`（依赖关系，回答"改 X 会影响谁"）

2. **task 视角 + repo 视角双读**：
   - doc-7 告诉你「In Progress 任务现在多少%」
   - REPO_STATUS.md 告诉你「65 个仓库中有几个长期静默 / 待激活」
   - 两份合起来才完整，**仅靠 doc-7 会漏掉 dormant 仓库的提醒**

3. **如果 doc-7 / REPO_STATUS 数据陈旧（> 7 天前）**：
   - 在输出中标注「数据来自 N 天前的扫描，建议先跑 /sync-progress」
   - 不要自动跑 sync-progress（耗时长），只提示

4. **关注静默仓库**：
   - REPO_STATUS.md 的「关注列表」中 🔴/💤 仓库要主动评估
   - 不一定每次都建议激活，但如果用户的季度/年度目标依赖某个静默仓库，必须明确提醒
   - 例：「TASK-13 Cos72 Core 35%，但 mycelium/MyVote 静默 44 天，本季要完成 Phase 1 需要本周激活 MyVote」

4.5. **执行 GOALS.md 中的 orchestrator 提醒规则**（强制）：
   - GOALS.md 中明文写了若干「时间 + 条件 = 必须提醒」的规则（如 ZUAEC 8-31 报名、AgentSocial 静默警报）
   - 每次响应前，对照今天日期检查每条规则，触发的条件必须**用红字 / 警示 emoji 主动提示**
   - 不可省略，即使用户没问 —— 这是 orchestrator 的主动职责

5. **不要堆砌信息**：
   - 介绍段 ≤ 200 字
   - 进度段 ≤ 一张表 + 5 个 bullet
   - 建议段每项 ≤ 5 行

6. **诚实**：
   - 如果某些任务 Wrapper 没活跃 commit，说"近期无明显进展"
   - 如果某个建议本质上还有 50% 工作量，**不要**说"2 周到 90%"，改说"4 周到 90%"

7. **聚焦交付**：
   - 优先建议「能上线/能发布/能演示」的事
   - 避免建议纯内部重构 / 文档清理（除非用户问）

## 用户原始诉求（设计意图，2026-05-20）

> "当有人让你介绍你自己的时候，你要除了给出介绍之外，还进行一次整体的进度的 review，
> 然后指出来我们要下一步要 focus 的重点。
> 因为整体进度，如果期望达到 [较高比例] 的话，那还有几个进度可能是之后的，
> 那你给出这个 suggestion 的建议来，
> 然后包括对应的仓库，以及它开发了当前进度，预期的进度。
> 比如说我 [集中精力] 一周或两周之后达到 90% 以上，
> 那你要给出这个建议。"

核心意图：**「介绍 ≠ 静态自述。介绍是和团队对齐当前位置 + 下一步该往哪儿冲。」**
