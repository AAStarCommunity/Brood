# 中国大陆 KMS/DVT 节点网络架构设计（修正版）

> 核心前提更正：KMS 不是本地私有服务，而是**对外提供 API 的网络服务**：
> 有公网域名、账户注册体系、签名 API 接口，需要被全球 DVT 节点调用。
>
> 更新：2026-07-07 v3

---

## 一、KMS 的真实定位

```
KMS = 对外运营的签名服务
  ├── 公网域名（如 kms.your-domain.com）
  ├── 账户注册 / API Key 管理
  ├── 签名 API（POST /sign，DVT 节点调用）
  └── 运行在用户自己的 MX93 上（用户掌控私钥分片，不托管给第三方）
```

用户自己持有 MX93 硬件 + 私钥 + KMS 软件，但 KMS 需要向全球 DVT 节点暴露 API。  
这是"**自托管但对外可访问**"的模式，类似自建的 Web3Signer / Dirk。

---

## 二、问题重述

| 组件 | 需要外网访问？ | 当前方案在中国的问题 |
|------|------------|------------------|
| KMS API（签名接口） | ✅ 是，全球 DVT 节点都要调用 | Cloudflare Tunnel 被封，无法穿透 GFW 入站 |
| KMS 管理 UI | ✅ 是，操作者需要访问 | 同上 |
| DVT 节点 p2p 端口 | ✅ 是，其他 DVT 节点通信 | 同上 |

三个都需要外网访问，三个都被 GFW 封锁入站。

---

## 三、核心架构：香港 VPS 作为统一入口

**设计原则**：MX93 所有对外连接由自己主动出站（GFW 不拦出站），香港 VPS 作为公网入口。

```
                        全球访问者 / DVT 节点
                               │
              ┌────────────────┼────────────────┐
              │                │                │
              ▼                ▼                ▼
     kms.domain.com    ui.domain.com    p2p.domain.com
              │                │                │
              └────────────────┼────────────────┘
                               │
                    A 记录统一指向香港 VPS 公网 IP
                               │
                               ▼
        ┌──────────────────────────────────────────────┐
        │              香港 VPS（公网 IP: 1.2.3.4）      │
        │                                              │
        │  ┌─────────────────────────────────────┐    │
        │  │  nginx 反向代理                       │    │
        │  │  :443 /api/* → frp → MX93:3000 KMS  │    │
        │  │  :443 /ui/*  → frp → MX93:8080 UI   │    │
        │  └─────────────────────────────────────┘    │
        │                                              │
        │  ┌─────────────────────────────────────┐    │
        │  │  frp server（内部端口 7000）           │    │
        │  │  接收来自 MX93 的主动隧道连接          │    │
        │  └─────────────────────────────────────┘    │
        │                                              │
        │  ┌─────────────────────────────────────┐    │
        │  │  libp2p relay daemon（端口 9000）     │    │
        │  │  DVT 节点 p2p 中继                   │    │
        │  └─────────────────────────────────────┘    │
        └──────────────┬───────────────────────────────┘
                       │
         frp 隧道（MX93 主动出站建立，GFW 不拦）
         libp2p 连接（MX93 主动出站建立）
                       │
                       ▼
        ┌──────────────────────────────────────────────┐
        │             中国境内 MX93 主板                 │
        │                                              │
        │  ┌──────────────────────────────────────┐   │
        │  │  KMS 服务（:3000）                    │   │
        │  │  ├── POST /sign（签名接口）            │   │
        │  │  ├── POST /account/register           │   │
        │  │  └── GET  /health                    │   │
        │  └──────────────────────────────────────┘   │
        │                                              │
        │  ┌──────────────────────────────────────┐   │
        │  │  管理 UI（:8080）                     │   │
        │  └──────────────────────────────────────┘   │
        │                                              │
        │  ┌──────────────────────────────────────┐   │
        │  │  DVT 节点进程（:8080）                 │   │
        │  │  └── 调用 KMS: localhost:3000（< 1ms）│   │
        │  └──────────────────────────────────────┘   │
        │                                              │
        │  ┌──────────────────────────────────────┐   │
        │  │  frp client（出站连接到 HK VPS:7000） │   │
        │  │  libp2p（出站连接到 HK relay:9000）   │   │
        │  └──────────────────────────────────────┘   │
        └──────────────────────────────────────────────┘
```

## 四、各条流量路径详解

### 路径 A：外部 DVT 节点调用 KMS 签名 API

```
EU DVT 节点
  1. POST https://kms.domain.com/sign
  2. DNS → A 记录 → 香港 VPS:443
  3. nginx 按路径路由 → frp server
  4. frp server 通过 MX93 预先建好的隧道发送请求
  5. MX93 frp client 收到 → 转发给 localhost:3000（KMS）
  6. KMS 处理签名（私钥分片在本地，不出机器）
  7. 响应原路返回

延迟（EU → HK ≈ 230ms，HK → MX93 ≈ 20ms）：
  单次 API 往返 ≈ 500ms
  Ethereum 出块窗口 12 秒，完全可接受
```

### 路径 B：MX93 上的 DVT 进程调用本机 KMS

```
DVT 进程（:8080）
  → localhost:3000（KMS）
  → 延迟 < 1ms
  → 私钥分片永不离开 MX93
```

### 路径 C：操作者访问管理 UI

```
操作者浏览器
  → https://ui.domain.com（或 kms.domain.com/ui）
  → 香港 VPS nginx
  → frp → MX93:8080
  → 管理界面
```

### 路径 D：其他 DVT 节点 p2p 通信

```
SG DVT 节点
  → 连接香港 VPS libp2p relay:9000
  → relay 将流量转发给 MX93 DVT 进程的 libp2p 连接
  → MX93 DVT 进程处理共识消息
```

## 五、DNS 配置

```
kms.domain.com    A    1.2.3.4    ; 香港 VPS，不走 CF 代理
ui.domain.com     A    1.2.3.4    ; 同一 VPS，或 CNAME 到 kms
p2p.domain.com    A    1.2.3.4    ; libp2p relay 端口
```

**不开 Cloudflare 橙色云朵**：这条链路走 frp 自己的 TLS，Cloudflare 代理反而添乱。  
**全球其他地区节点**继续用 Cloudflare Tunnel（橙色云朵打开），两套方案并行。

| 调用路径 | 延迟估算 | 是否可接受 |
|---------|---------|-----------|
| MX93 DVT → 本机 KMS | < 1ms | ✅ 完美 |

## 七、香港 VPS 单点问题

香港 VPS 是这套方案的单点，需要考虑：

**监控**：对 kms.domain.com 做健康检查，HK VPS 挂了立即告警

**冷备方案（成本极低）**：
```
平时：kms.domain.com A → HK VPS（1.2.3.4）
故障：手动或自动切换 A 记录 → 新加坡备用 VPS（5.6.7.8）
      新加坡 VPS 上跑同样的 frp server，MX93 同时维持两条隧道
```

**MX93 同时连两个 relay**（双出站隧道，frp client 配置两个 server）：
```toml
# frpc.toml 同时连接香港和新加坡
serverAddr = "hk-vps"     ; 主
serverAddr = "sg-vps"     ; 备
```
