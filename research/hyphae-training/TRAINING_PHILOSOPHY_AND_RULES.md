## 1. 用户原始洞察（结构化记录）

### 1.1 中小组织的核心诉求（2-3 个）

> 用户原话：**"中小组织他核心的诉求也就这么两三个。"**

**诉求一：获客（Customer Acquisition）**
- 不能孤立看"获客"，必须看大量上下文：
  - **行业**（餐饮 / 律所 / 制造 / 教育 / ...）
  - **地区**（一线 / 二三线 / 县城 / 乡村；不同地区客流和竞争完全不同）
  - **竞争环境**（红海 / 蓝海 / 寡头 / 完全竞争）
  - **当下经营状况**（垂死挣扎 / 收支平衡 / 欣欣向荣）
- **不同上下文 → 完全不同的获客策略**
- 例子：垂死挣扎需要"短期回血"打法，欣欣向荣需要"扩大规模"打法

**诉求二：流程高效低成本运转（Operations Efficiency）**
- 例子：蛋糕店是否参加集市，决策涉及多维度：
  - 天气（雨天集市没人）
  - 库存（库存高需要清，库存低不能再做）
  - 人员结构（人手够不够支撑额外活动）
  - 季节（节假日 vs 平时）
  - 主理人当下状态（精力 / 心态）
- **决策本身是综合的，工作流程是动态的**
- 每月可能调整，每个季度可能变化
- 大流程套小流程（参加集市 → 子流程：打海报 / 招呼客户 / 现场支付 / 售后跟进）

**诉求三（隐含）：战略决策（Strategic Direction）**
- 每年 / 每阶段重点不同：
  - 这阶段就是**盈利**
  - 这阶段就是**扩大客户规模**
  - 这阶段就是**提升客户服务质量**
- 战略决策又和大量信息 + 上下文 + 外界影响因素有关

### 1.2 普通中小组织主理人的真实困境

> 用户原话：**"普通的人可能有一些知识点或者是学习借鉴、抄袭无所谓。但是他没有全面的上下文和整个人类文化背景的知识库。"**

- 有零散知识（朋友圈 / 抖音学的）
- 没有系统知识库
- 没有上下文整合能力
- 没有跨领域类比能力

→ **决策质量天花板被"个人知识结构"卡死**。

### 1.3 Hyphae 提供的核心价值

> 用户原话：**"我们是能够提供这个方式去思考，给出他一个真正的智能体安排的协作工作流程是一个高效的 SOP。"**

- 提供**思考方式 + 工作流程 SOP**
- 像贴身定制的**动态 ERP+CRM**
- 帮助中小组织完成**核心目标**（盈利 / 扩客 / 提质）

### 1.4 训练的双层结构：框架 + 内容

> 用户原话：**"我们预训练什么东西，实际上是要有框架和这个内容的框架。"**

**框架（如何思考）**：
- 三大核心诉求 → 决策维度
- 上下文 → 决策因子
- 子流程展开 → 行动方案

**内容（具体能力 + 资源）**：
- 通用能力（举例）：
  - 海报制作
  - 合作伙伴选择
  - 活动报名
- 注入资源 / 上下游 → 匹配出最佳方案

### 1.5 一句话总结（用户原意）

> **"帮助中小组织在自己的核心目标（盈利 / 扩客 / 提质）上，用全面上下文 + 人类文化背景知识库做出最佳决策 + 输出可执行的动态 SOP — 这是 Hyphae LoRA 训练的本质。"**

## 2. 我的提炼：训练对象的三层结构

基于用户洞察，我把"要训练什么"提炼为三层：

```
┌──────────────────────────────────────────────────────────────────┐
│  Layer 1 — 思考框架（Meta-Cognition）                              │
│  ─ 三大诉求识别：当前阶段是获客 / 提效 / 战略调整？                  │
│  ─ 上下文采集：哪些因子要考虑？                                     │
│  ─ 决策路径生成：如何从因子到行动？                                  │
│  ─ SOP 编排：把决策展开为可执行子流程                               │
│  → 这部分是 LoRA 训练的"基本盘"（人格 / 思考方式）                  │
├──────────────────────────────────────────────────────────────────┤
│  Layer 2 — 通用能力（General Capabilities）                       │
│  ─ 海报制作 / 文案撰写 / 报价单 / 邮件 / 公众号文章                  │
│  ─ 合作伙伴评估 / 活动报名 / 客户拜访话术                            │
│  ─ 数据看板解读 / 财务分析基础                                      │
│  → 开源大模型已经会，少量微调即可（重点是行业语境适配）              │
├──────────────────────────────────────────────────────────────────┤
│  Layer 3 — 具体内容（Contextual Data）                            │
│  ─ 该客户的产品 / 客户名单 / 库存 / 历史交易                         │
│  ─ 该客户的合作伙伴 / 供应商 / 渠道                                 │
│  ─ 外界实时数据：天气 / 行业新闻 / 竞品动向 / 政策                  │
│  → 走 RAG + 实时 API，不进 LoRA 权重                               │
└──────────────────────────────────────────────────────────────────┘
```

> ⭐ 关键论断：**LoRA 训练 Layer 1 + Layer 2，RAG / Agent 处理 Layer 3**。混淆这三层是 80% AI 项目失败的原因。

## 3. 我的反馈和建议（5 条）

### 3.1 建议 1：明确分层，避免"什么都想训进 LoRA"

用户的洞察非常深 —— 但容易让团队陷入"想把所有东西都训到 LoRA 里"的陷阱。

**正确分工**：
- **LoRA / Fine-tuning**：训练 Layer 1（思考框架）+ Layer 2（行业风格语境）
- **RAG**：处理 Layer 3 中的静态知识（合同库 / 商品库 / 历史交易）
- **Agent + Tool**：处理 Layer 3 中的动态数据（天气 API / 行业新闻 / 实时库存）
- **Workflow Engine**：处理 SOP 执行（n8n / Temporal / Dify）

### 3.2 建议 2：双层 LoRA 架构（行业 LoRA + 客户 LoRA）

不要为每个客户单独训练完整 LoRA。架构：

```
Base Model (Qwen 2.5 14B)
   │
   ├─ 行业 LoRA（HyperCapital 维护）—— "蛋糕店思考方式" / "律所思考方式"
   │  └─ 由联邦学习从该行业多家组织汇集（v2）
   │  └─ 或由 HyperCapital 行业顾问 + GPT-4 合成数据（v1）
   │
   └─ 客户 LoRA（每客户小增量）—— "本店的语气 / 本店的客户类型 / 本店的常见决策"
      └─ 仅 3-5% 训练步数
      └─ 在客户机房或 TEE GPU 跑
```

**优势**：
- 训练成本 90% 节省
- 行业 LoRA 一次训完万家共享
- 客户 LoRA 只调最后几层，保护隐私

### 3.3 建议 3：先做"高频窄场景"，不要一上来做"全息决策"

中小组织 90% 客户最先要的不是"战略决策助手"，而是**"帮我写明天的朋友圈"**。

**产品分层**：

| 层级 | 产品形态 | 客户占比 | LoRA 训练复杂度 |
|:---|:---|:---:|:---:|
| **入门** | "AI 文案 + 海报助手"（写朋友圈 / 公众号 / 海报）| 60% | 低（Layer 2） |
| **标准** | "业务流程辅助"（库存提醒 / 客户分类 / 复购触发）| 30% | 中（Layer 1+2） |
| **进阶** | "战略决策辅助"（季度复盘 / 增长建议 / 风险预警）| 10% | 高（Layer 1+2+3 全栈） |

⭐ **Lite 版做"入门"** —— 跑通后再加"标准" / "进阶"。

### 3.4 建议 4：数据稀缺是真正的护城河

用户提的能力（海报、合作伙伴选择、活动报名）开源大模型基本都会。**真正稀缺的是"中国中小组织特定场景下的判断范式数据"**。

例子：
- "杭州的蛋糕店在 6 月份的雨天，库存 80%，前 1 周营业额下降 15%，员工 3 人有 1 人请假 —— 是否参加周末集市？"
- 这种"全因子综合判断 → 最终决策"的样本，**全网几乎没有**

**Hyphae 需要做的**：
1. **创始人访谈** —— 通过 10 年 ERP 网络访谈 100 位中小组织主理人，收集真实决策案例
2. **合成数据** —— 用 GPT-4o / Claude Opus / DeepSeek V3 基于真实案例扩充 10-100 倍
3. **Mycelium 共建** —— 开源数据集，让社区贡献本行业经验
4. **联邦学习** —— v2 阶段从多家同行业客户聚合判断模式

→ **数据 = Hyphae 最深的护城河**（Firework 永远拿不到这种数据）。

### 3.5 建议 5：把"训练哲学"作为对客户的核心叙事

向客户卖 Hyphae 时，不要讲 "我们用 LoRA / QLoRA"（客户听不懂），讲：

> **"我们给你的不是一个 AI，是一个懂你这个行业、懂你这家店、能像老炮儿一样和你一起决策的'数字合伙人'。"**

这才是用户洞察的真正商业价值。

## 4. 10 个挑战式问题 + 我的建议回答

> 自我挑战 —— 找出用户洞察中可能的弱点，并给出建议。

### 挑战 1：用户说"动态 ERP+CRM"是极其宏大的概念，中小组织真的需要这种"全息上下文"吗？

**问题**：传统 ERP / CRM 软件之所以贵且复杂，正因为它们试图覆盖"全息"。Hyphae 想做更轻量的，但又要"全息上下文"，是不是矛盾？

**建议回答**：
- 矛盾的解决在**渐进式**：
  - Lite 版只做"业务流程辅助"（Layer 2 + Layer 3 静态部分）
  - 不要一开始做"战略决策辅助"
- "全息上下文"的等级分层：
  - **基础**（必须）：组织内部数据（员工 / 客户 / 商品 / 历史交易）
  - **进阶**（可选）：行业 / 地区 / 季节模板
  - **高级**（v3+）：外界实时数据（天气 / 新闻 / 竞品）
- 不要把客户的"想要"等同于"产品边界"

### 挑战 2：你说要"训练思考框架"，但开源大模型（GPT-4 / Claude / Llama）已经会基础推理 + 业务分析。再训 LoRA 边际收益多大？

**问题**：海报制作、合作伙伴评估、邮件撰写这些能力，Qwen 2.5 14B 已经做得不错。LoRA 训练的边际收益不明显，可能不值这个成本。

**建议回答**：
- 真正训的不是"能力"而是"判断范式"：
  - 开源模型会写**通用海报**，不会写**"杭州小蛋糕店周末集市低成本吸引客流"的海报**
  - 开源模型会评估**通用合作伙伴**，不会评估**"中国二线城市烘焙业上下游"**
- 训练**应该约束 + 简化 + 本地化模型输出**：
  - 约束：输出不超过 X 字、用 X 风格、引用 X 文化背景
  - 简化：复杂分析变成结构化输出（决策表 / SOP 卡片）
  - 本地化：用中国中小组织听得懂的话
- **如果开源模型已足够，那就只做 RAG + Prompt 工程，不强训 LoRA**
  - HyperCapital 销售要诚实告诉客户"你的场景需要 LoRA 吗？"
  - 不需要的客户卖 RAG + Agent，便宜还效果好

### 挑战 3：每个客户业务都独一无二，训练 10000 个客户岂不要 10000 个 LoRA？维护成本爆炸

**问题**：客户 LoRA 个性化训练听起来美好，运维就是地狱。10000 个 LoRA 怎么版本管理 / 监控 / 更新？

**建议回答**：
- **双层 LoRA 架构**（见建议 2）—— 行业 LoRA 1 个，客户 LoRA 10000 个
- 客户 LoRA 设计为**极小**（rank 4 / 8）—— 训练 10 分钟，存储 50MB
- vLLM **Multi-LoRA 热加载**架构：1 张 GPU 同时服务 100+ 客户 LoRA
- HyperCapital 包 B 自动化：
  - 月度增量训练（脚本化）
  - 自动 A/B 测试新 LoRA vs 旧 LoRA
  - 客户授权后自动滚动更新
- v3+ 引入 **MoLE**（Mixture of LoRA Experts）—— 根据请求动态路由 LoRA

### 挑战 4：战略决策依赖**外界实时数据**（天气 / 新闻 / 竞品）。这些动态的，不可能预训练到 LoRA 里

**问题**：你说"战略决策与外界因素有关"，但 LoRA 权重一旦训完就静态了。怎么处理这种动态？

**建议回答**：
- LoRA 训的是 **"如何分析"**（推理框架），不是 "**分析结果**"
- 实时数据走 **Agent + Tool**：
  - 天气：调和风天气 API
  - 行业新闻：调虎嗅 / 36 氪 RSS + Embedding 实时检索
  - 竞品：调蓝海情报 / 内部爬虫
- LoRA + RAG + Agent 三层协作：
  - Agent 获取实时数据 → 喂给 RAG 检索相关历史模式 → LoRA 给出"杭州蛋糕店周末雨天 + 库存高 + 员工少时的推荐决策"
- 客户得到的不是"硬规则"而是"参考决策 + 理由"

### 挑战 5：你说要做"贴身定制 ERP+CRM"。但 ERP / CRM 本质是**数据库 + 工作流引擎**，LoRA 是**语言模型**。两者怎么结合？

**问题**：传统 ERP（如金蝶 / 用友 / Odoo）是表格 + 流程，LoRA 是自然语言。你说"贴身定制 ERP+CRM"是要替代它们还是包装它们？

**建议回答**：
- **不替代，是 AI 顾问层 + 调度层**：
  - 客户已有的 ERP / CRM / 微信收银 / 钉钉 / 飞书 —— **全部保留**
  - Hyphae 通过 API / MCP 接入这些系统作为**数据源 + 执行器**
  - LoRA + Agent 是上面的"AI 顾问"，告诉系统怎么动
- 架构示例（蛋糕店）：
  ```
  客户系统：微信小程序订单 + 美团外卖 + Excel 库存 + 钉钉员工排班
              ↓ API 接入
        ┌───── Hyphae Agent24 ─────┐
        │  调用工具：查询 / 写入       │
        │  调用 LoRA：判断 / 决策      │
        │  调用 RAG：行业知识         │
        └────────────┬────────────┘
                     ↓
        给主理人输出：今日决策卡 + SOP
  ```
- **不是替代 ERP，是把 ERP / CRM 变得"会说话 + 会建议"**

### 挑战 6：训练数据从哪来？真实中小组织主理人**不会**愿意把"经营秘密 / 决策过程"贡献给我们

**问题**：你说"创始人访谈 100 位中小组织主理人"听起来美好，但主理人凭什么把"亏损 / 决策失误 / 客户秘密"告诉你？

**建议回答**：
- **三个层次的数据来源**：
  1. **公开数据**：抖音 / 小红书 / 微博 / 知乎上中小组织主理人**自己分享**的经验（爬取 + 清洗）
  2. **创始人 ERP 网络付费访谈**：每位主理人付 ¥500-2000，签 NDA + 匿名化使用
  3. **合成数据**：用 GPT-4 / Claude 基于公开案例生成 synthetic 决策样本
- **合成数据是主力**（覆盖 70-80% 训练量）—— Stanford Alpaca / Vicuna 已证明可行
- **真实数据是质量基准**（20-30% 训练量）—— 用于评测和精调
- **Mycelium 共建**：开源数据集 + 社区贡献者贡献本行业经验（参考 OpenAssistant 模式）

### 挑战 7：所有这些"全息上下文"对客户数据隐私是**双刃剑**

**问题**：要做"全息决策"必须读客户内部数据（财务 / 客户 / 库存 / 员工）。这些一旦泄露损失巨大。怎么保证？

**建议回答**：
- 已在 [PRIVACY_PRESERVING_TRAINING.md](./PRIVACY_PRESERVING_TRAINING.md) 详细设计：
  - **本地模式**：数据 + 训练全在客户机房
  - **TEE 模式**：加密上传 H100 CC，我们看到的全是密文
  - **联邦模式**：多组织协作，数据不出门
- 额外措施：
  - 客户 LoRA **不存原始数据**，只存"模式权重"
  - 第三方审计（NVIDIA Remote Attestation）
  - 客户拥有 LoRA 权重的完整版权 + 可随时撤回 / 销毁
- 法律：律师函 + ToS 明示

### 挑战 8：你说"训练框架 + 内容"听起来像 Anthropic 的 Constitutional AI。Hyphae 没那个团队 + 钱

**问题**：Anthropic 训 Claude 用了 100 亿美元 + 几百个 PhD。我们说要训"思考框架"是不是过于野心？

**建议回答**：
- **不复刻 frontier 研究**，套用现成方法：
  - Base model 用开源（Qwen 2.5 / DeepSeek V3）
  - PEFT 方法用现成（LoRA / DoRA）
  - 训练框架用 LLaMA-Factory（不自研）
- **创新点在数据 + Prompt 工程 + 行业模板，不是算法**
- "训练思考框架"实际操作是：
  - 准备 10k-100k 高质量"输入（上下文）→ 输出（决策 + 理由）"样本
  - QLoRA 微调 14B 模型
  - 评测对比 base model（GPT-4 as judge）
- 算法门槛不跨，业务护城河深挖

### 挑战 9：中小组织主理人不一定会按你的"SOP 卡片"行动。怎么保证 Hyphae 输出**真正被采用**？

**问题**：很多 AI 工具失败不是因为质量差，而是用户不愿改变习惯。你给老板"今日决策卡"，他凭什么听你的？

**建议回答**：
- **不要试图替代主理人决策，做"决策辅助 + 备选方案"**：
  - 不说"你应该做 X"，说"我推荐 X，因为 ABC；备选 Y/Z"
  - 主理人保留**最终决策权 + 修改权**
  - 学习主理人的"实际行动"反过来微调下次推荐
- **从执行层切入而非决策层**：
  - 先做"帮你写朋友圈"（必采纳，因为本来就要写）
  - 再做"帮你算库存"（高频用）
  - 最后做"帮你决定参不参加集市"（决策层，进入慢）
- 评测指标不是 LoRA 准确率，是**"主理人 30 天保留率"** + **"主理人主动询问频次"**

### 挑战 10：所有这些设计的**护城河**到底有多深？随便一个团队用同样的 LLaMA-Factory + LoRA + RAG 都能复制

**问题**：技术栈全是开源的，思路也写在文档里。竞争者抄袭门槛极低，护城河在哪？

**建议回答**：
- **真正的护城河不在技术栈，在三个东西**：
  1. **行业数据 + 标注质量**（创始人 30 年软件 / ERP 网络 + 持续访谈）
  2. **行业 LoRA 库 + 持续迭代**（每个行业 1 个高质量 LoRA，竞争者要从零开始）
  3. **HyperCapital 商业服务网络**（人 + SOP + 客户关系，竞争者一年也培养不出）
- **技术栈不是护城河**：
  - Firework AI 估值 $150 亿，但他们的护城河也不是 vLLM
  - 真正护城河是 PyTorch 团队 + 客户名单 + 数据
- Hyphae 的对应护城河：
  - 团队 = 创始人 + David + 行业顾问网络
  - 客户名单 = Mycelium / FangPay 共享 ICP
  - 数据 = 中国中小组织决策样本（独家）
- **写得清的护城河不是真护城河**。真护城河是"知道但做不到"

## 5. LoRA 训练指导规则（V0.1，可操作）

### 规则 1 — 三层分清楚

| 训练对象 | 用什么 | 例子 |
|:---|:---|:---|
| Layer 1 思考框架 | **LoRA** | "如何决定参加集市" |
| Layer 2 通用能力 | **LoRA**（轻量）或 **base 直用** | 海报 / 文案 / 邮件 |
| Layer 3 具体数据 | **RAG + Agent** | 库存 / 客户名单 / 实时天气 |

**违规**：把"客户名单"训进 LoRA 权重 → 严重错误。

### 规则 2 — 双层 LoRA 架构

```
Base (Qwen 2.5 14B) + 行业 LoRA + 客户 LoRA
```

- 行业 LoRA：HyperCapital 维护，跨客户共享
- 客户 LoRA：rank 4-8，仅 3-5% 训练步数，10 分钟训完

**违规**：每客户都训"完整 LoRA" → 运维爆炸。

### 规则 3 — 产品分层

| 层级 | 训练复杂度 | Lite 是否做 |
|:---|:---:|:---:|
| 入门（文案 / 海报） | 低 | ✅ |
| 标准（业务流程） | 中 | ❌ v1.5 |
| 进阶（战略决策） | 高 | ❌ v2 |

**违规**：Lite 阶段做"全息决策" → MVP 跑不通。

### 规则 4 — 数据三七法则

| 来源 | 占比 | 用途 |
|:---|:---:|:---|
| 合成数据（GPT-4 / Claude 生成）| 70% | 训练主力 |
| 真实访谈（创始人 ERP 网络）| 20% | 质量基准 + 评测 |
| 公开数据（抖音 / 小红书清洗）| 10% | 风格语境 |

**违规**：100% 合成数据 → 模型脱离实际 / 100% 真实数据 → 数据不够。

### 规则 5 — 评测指标用业务而非技术

| 不要看 | 要看 |
|:---|:---|
| MMLU 分数 | "主理人 30 天保留率" |
| BLEU / ROUGE | "推荐 SOP 被实际采纳率" |
| Perplexity | "主理人主动询问频次" |

**违规**：用学术 benchmark 评中小组织产品 → 误导决策。

### 规则 6 — 隐私必须分级

| 客户数据敏感度 | 训练模式 | 训练位置 |
|:---|:---|:---|
| 低（公开商品 / 公开活动）| 本地 / TEE 均可 | 客户自定 |
| 中（库存 / 销售）| 优先本地，可 TEE | 客户机房 |
| 高（财务 / 客户身份）| **必须本地或 TEE** | 客户机房（v1） |
| 极高（医疗 / 法务卷宗）| **必须本地** | 客户机房（含 v2）|

**违规**：高敏感数据上普通云 GPU 训练 → 监管 + 信任双崩。

### 规则 7 — 不要训进 LoRA 的东西

❌ 客户姓名 / 手机号 / 身份证号
❌ 公司财务报表数字
❌ 商品 SKU 详情
❌ 实时库存
❌ 邮件原文
❌ 法律卷宗原文

→ **这些走 RAG**。

### 规则 8 — 必须训进 LoRA 的东西

✅ "蛋糕店决定参加集市的思考维度"（不含具体数字）
✅ "杭州二线城市 30 人小店的语气风格"
✅ "中国餐饮业获客的常用 8 种打法 + 适用场景"
✅ "客户复购触发的 5 种信号模式"

→ **这些是范式 / 风格 / 框架，应该进 LoRA**。

### 规则 9 — Constitution（输出宪法）

每个客户的 LoRA 输出必须遵守：
- 给出 2-3 个备选方案（不强推单一答案）
- 每个方案给出"为什么"（理由可被主理人质疑）
- 标注不确定性（"在 X 条件下推荐 Y，但若 Z 变化建议 W"）
- 不输出违法 / 违规内容（赌博 / 色情 / 政治）
- 中文优先，专业术语后跟解释

**违规**：输出"上帝口吻"硬建议 → 客户反感。

### 规则 10 — 持续学习闭环

```
客户用 LoRA 输出 → 主理人采纳 / 修改 / 拒绝
                     ↓
          记录"实际行动"作为新样本
                     ↓
           月度增量 LoRA 训练
                     ↓
          客户 LoRA 越来越懂客户
```

**违规**：训完 LoRA 不迭代 → 一年后过时。

## 6. 实际操作示例：杭州小蛋糕坊"星妈烘焙"

### 6.1 客户档案

- 行业：烘焙 / 蛋糕零售
- 地区：杭州二线区域（萧山区）
- 规模：3 人（老板 + 2 员工）
- 月流水：¥6-10 万
- 主要客户：年轻妈妈群（30-40 岁）
- 当前阶段：**收支平衡，想扩客**
- 已有系统：微信小程序订单 + 美团外卖 + 微信支付 + Excel 库存

### 6.2 Hyphae 训练设计

**Base model**：Qwen 2.5 14B
**行业 LoRA**：HyperCapital "烘焙零售 LoRA"（共享）
**客户 LoRA**：星妈定制版（rank 8，500 样本）

**训练样本示例**（"星妈定制 LoRA"）：

```jsonl
{"input": "今天是周六，下雨，天气预报全天阴雨。库存：奶油蛋糕 8 个 / 蛋挞 30 个 / 面包 50 个 / 奶油储备低（2L）。客户群昨日活跃度低。员工今日全到岗。我下午有空，要不要做点什么吸引客户？", 
 "output": "推荐 3 个方案：\n1. 雨天'到店送'活动：朋友圈推送'雨天到店出示截图送小奶油泡芙' — 适合：库存压力中等 + 你下午有空。\n2. 蛋挞清库存预定：发起'明天蛋挞预定 9 折' — 适合：蛋挞库存高 + 周日早晨配送可消化。\n3. 等等：什么都不做，库存不算太高，明天周日客流自然回升 — 适合：你想节省精力。\n建议优先方案 1，理由：雨天到店成本低 + 你有时间 + 转化新客效果好。但奶油储备低，方案 1 限定 30 份。"}
```

### 6.3 Layer 3（RAG + Agent）连接

```
查实时天气 → 和风天气 API
查库存 → 接星妈 Excel + 微信小程序后台
查活跃度 → 接微信群活跃度（人工录入）
查美团评分 → 美团商家后台 API
```

### 6.4 客户输出形态

每天早晨 7:30，星妈老板收到企业微信推送：

```
🌅 早，星妈烘焙今日参考决策（2026-06-23 周六）

  · 天气：今天有雨 ☔
  · 库存：奶油蛋糕 8 / 蛋挞 30 / 面包 50 （蛋挞库存偏高）
  · 客户群昨日活跃：低
  · 美团评分：4.6 ⭐（本周保持）
  · 员工：全到岗

🎯 今日推荐 3 个方案（任选）：
  1️⃣  雨天到店送泡芙活动（预计触达 80 人 / 转化 5-8 单）
  2️⃣  蛋挞预定 9 折（清库存 + 储备明日订单）
  3️⃣  休息日，让数据自然走

💡 我会推荐：方案 1 +（夜晚做方案 2 群发）
   理由：雨天客流少，活动能拉拢新客；蛋挞库存压力大需要清

[ 采纳 ]  [ 修改 ]  [ 拒绝 ]
```

主理人点击 → 数据回传 → 下月 LoRA 自动增量训练。
