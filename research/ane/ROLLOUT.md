# iDoris.ai 的打法(GTM)—— 三例证 → 双资产 → 扩张,及四个警告

> **来源**：用户 2026-07-14 第四轮口述。
> **状态**：v0.1(2026-07-14)。
> **上游**：[ORG_MODEL.md](./ORG_MODEL.md)。本文回答其"暗礁一(先打谁)"与"暗礁三(变现)"。

## 0. 一句话

**边做真实场景、边提炼流程与工具**:三个月内,给"个体 / 社区组织 / 商业公司"各落一个初步案例;三案例沉淀出**左=工具与流程、右=客户信任**两份资产,再以此扩张。变现靠"效率分成"(帮商业公司省 30%、收 5% 提成)。

## 1. 打法(用户口述)

**核心节奏**:围绕三角色找真实场景,**一边开发一边提炼流程/工具**,一边把实际问题做好。服务三类对象:

| 服务对象 | 现有抓手 | 目标 | 状态 |
|:---|:---|:---|:---|
| **个体** | **每周六 CNX 本地 AI builder 聚会**——交流个体想法(可解个体问题,也可解组织问题) | 大小工具解决细分/通用问题 | 有抓手 |
| **社区 / 组织** | **暂无承接点** | 帮组织/社区实现**可持续**(公益=活下去,商业=赚钱) | 缺口 |
| **商业公司** | 焦虑地找人帮它 AI native、提效、在竞争中不败乃至取胜 | 提效保竞争力 | 有诉求,未接 |

**约束**:就这么几个人,时间精力有限,不敢接太多。

**里程碑**:三案例(个体/社区/商业)~3 个月内落地,至少迭代出初版。

**扩张(下一步,两个方向)**:
1. 供给侧——服务表达者/创新者/建设者的流程已打通,沉淀工具/框架/沟通流程;并给建设者、创新者乃至表达者提供**有例证的工作机会**。
2. **双资产沉淀**:
   - **左 = 工具 + 流程**(供给侧能力)
   - **右 = 客户信任**(需求侧信誉):个体看到"AI 确实帮到我"、社区看到"值得试试"、商业公司最现实——"真能提效我就分你钱"。

**变现**:效率分成——"帮我省 30%,给你 5% 提成"(30% 人力年成本可观)。用户自评"有点血淋淋,但商业经济没有人情"。

## 2. 这套打法解了两个暗礁

- **暗礁一(先打谁)**→ 答:**proof-then-scale**。不靠纯布道,用三个例证制造醒悟。
- **暗礁三(变现)**→ 答:**效率分成**(gain-share)。

## 3. 四个警告(现在这个人力规模下最该警惕的)

### ⚠️ 警告一:"三段各打一个"是**反聚焦**,n=1 不是证明,是轶事
- 3 个人分摊到三个差异极大的段(个体/社区/商业),很可能落成**三个半成品浅案例**,而非一个可信参照。
- 商业买家对 n=1 天然打折("对他们有用≠对我有用")。**单个案例是轶事,不是证据。**
- **建议(Crossing the Chasm 滩头逻辑)**:选**一个滩头段**打深——大概率是**商业公司**(付费意愿最清晰),在这一段做 2–3 个案例形成密度,再横向扩。三段齐开是这个阶段最大的稀释风险。

### ⚠️ 警告二:效率分成有"**度量与归因**"陷阱
- Gain-share 要求你**可信地度量"省了多少"并归因到你的介入**。实务上极易翻车:基线争议(是 30% 还是本来就会改善?)、归因争议、客户在事后**低报收益**的动机。
- **缓解**:小额固定费(覆盖成本 + 过滤不认真的客户)+ **带上限的**分成上行;或第一个度量周期后**转固定价**。纯分成合同常死在度量上。

### ⚠️ 警告三:**价值观断层**——"砍 30% 人力"与"数字公共物品/普通人福祉"的使命冲突
- 生态使命是"让普通人享受数字基础设施的福祉"([MISSION.md](../../protocol/MISSION.md));而商业变现机制是"提效=减人力成本"。**被砍的 30%,是不是使命要服务的"普通人"?**
- 这不是要否掉分成模式,而是**叙事接口必须自圆其说**:对外要能同时讲通"我帮你砍 30% 人力"和"我为普通人做数字公共物品"。否则这条断层会在传播时被抓住。
- **可能的和解**:把分成收入明确导向补贴个体/社区两段(交叉补贴),让"商业提效"反哺"普通人福祉",形成闭环叙事,而非纯粹的降本外包。

### ⚠️ 警告四:三段**不是三条对等的收入线**,别当三个生意做
- **商业公司 = 养组织的钱**;**个体(周六聚会)= 漏斗顶 + 人才供给 + 使命兑现**;**社区 = 痛点来源 + 中间信任**。
- 说白了是**交叉补贴结构**,不是三个平行营收。看清这点,资源分配才不会平均用力。

## 4. 把飞轮画出来(用户已有全部零件,只是没命名)

```
周六聚会(个体) ──招募──► 建设者/创新者
      ▲                      │
      │                      ▼ 解决
   收入反哺            社区/商业的真实痛点(Cos72 需求侧)
      │                      │
      │                      ▼ 做成例证
  商业客户付费 ◄──信任── 左=工具/流程 + 右=客户信任
```

- **飞轮**:聚会招才 → 才解痛点 → 痛点变例证 → 例证生信任 → 信任带来付费商业客户 → 收入反哺聚会与工具 → 更强的才。
- **当前断点**:社区/组织段"暂无承接点"——飞轮中段缺一环。**Cos72 应优先补这里**(见 [ORG_MODEL §4](./ORG_MODEL.md#4-与生态的接口))。
